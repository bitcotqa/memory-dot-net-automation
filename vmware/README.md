# VMware HCL Part Data Validation

Validates a "master" list of storage parts (SSD/HDD) that are supposed to be
listed on the Broadcom VMware Hardware Compatibility Guide against the actual
live data for those same parts, and reports exactly which columns are
correct, wrong, or missing — per record.

## Why this exists

`VMWARE_1.csv` is a master/export file of SSD and HDD part records (OEM,
part number, capacity, interface, DWPD, full spec dict, etc.) that is meant
to describe real entries on the Broadcom Compatibility Guide
(`compatibilityguide.broadcom.com`). Before that file is trusted or shipped
downstream, it needs to be checked against what the Compatibility Guide
actually says for each part — catching typos, digit transpositions, and
corrupted fields introduced anywhere upstream (manual entry, an import
script, etc.).

`vmware_playwright.csv` is the ground-truth counterpart: the same set of
parts scraped directly from the live Broadcom site with Playwright. Every
row in both files carries the same Broadcom `productId` in its `part_url`,
so rows can be matched 1:1 across files even when every other column in the
master file is wrong.

## What the automation does

1. **Match** each row in the master CSV to its counterpart in the
   playwright/ground-truth CSV via the `productId` query parameter in
   `part_url`.
2. **Compare, column by column**: Part Number, DWPD, Form Factor, Capacity,
   MFR Part No, Part Description, Interface, and every individual attribute
   inside the nested `part_specification` dict (Model, Endurance, Flash
   Technology, DWPD, VID/DID/SVID, etc.).
3. **Classify each column as one of three states**:
   - `MATCHED` — values agree
   - `MISMATCH` — both sides have a value, but they disagree
   - `MISSING` — one side (or both) has no value (blank / `nan` / `N/A`)
4. **Roll up** to a per-record `Overall Result` (`MATCHED` / `PARTIAL MATCH`
   / `UNMATCHED`) and a workbook-level `Summary` sheet with matched/mismatch/
   missing counts per column, so the noisiest columns are obvious at a
   glance.

A second, smaller check (`check_spec_attribute_naming.py`) looks at a single
CSV in isolation and flags rows whose `part_specification` dict is missing
an attribute key that the rest of its category (ssd/hdd) normally carries,
or that uses a misspelled key name instead (e.g. `'Flash'` instead of
`'Flash Technology'`) — useful for catching schema drift before it even gets
compared against the live site.

## Findings on the sample 10-record batch in `input/`

Every one of the 10 sample records had at least one hard mismatch against
the live site. Worst offenders: **MFR Part No** (10/10 wrong), **Capacity**
and **Part Number** (9/10 wrong each). Full detail is in
`output/VMWARE_Part_Validation_Report.xlsx`.

| Column | Matched | Mismatch | Missing |
|---|---|---|---|
| Part Number | 1 | 9 | 0 |
| DWPD | 5 | 0 | 5 |
| Form Factor | 6 | 4 | 0 |
| Capacity | 1 | 9 | 0 |
| MFR Part No | 0 | 10 | 0 |
| Part Description | 1 | 5 | 4 |
| Interface | 4 | 6 | 0 |
| Part Specification (attributes) | 131 | 10 | 8 |

## Usage

```
pip install -r requirements.txt

# full cross-file validation report
python validate_vmware_parts.py [expected.csv] [actual.csv] [output.xlsx]

# single-file spec-attribute naming check
python check_spec_attribute_naming.py [input.csv] [output.csv]
```

Both scripts default to the files under `input/` and write to `output/`
when run with no arguments.

## Files

- `validate_vmware_parts.py` — cross-file column validator (the main tool)
- `check_spec_attribute_naming.py` — single-file spec-key completeness check
- `requirements.txt` — Python dependencies
- `input/VMWARE_1.csv` — sample master/export file to validate
- `input/vmware_playwright.csv` — ground-truth data scraped from the live
  Broadcom Compatibility Guide via Playwright
- `output/VMWARE_Part_Validation_Report.xlsx` — full column-by-column
  MATCHED/MISMATCH/MISSING report + Summary sheet (generated by
  `validate_vmware_parts.py`)
- `output/VMWARE_1_vs_Playwright_Diff_Report.csv` — flat per-row diff
  listing exactly which of the 10 core columns differ and how
- `output/Comments_Missing_Report.csv` — spec-attribute naming/completeness
  check (generated by `check_spec_attribute_naming.py`)
- `output/vmware_part_validation_result_50_25SSD_25HDD.xlsx` — the original
  50-record (25 SSD / 25 HDD) reference validation report this tool's report
  format was matched against, with its `NOT APPLICABLE` result cells folded
  into `MATCHED` (nan/N/A on either side is treated as a non-issue, not a
  distinct status)
